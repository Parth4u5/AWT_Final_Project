# ADR-006: Keep MongoDB Atlas rather than migrate to Postgres

- **Status:** Accepted
- **Date:** 2026-11-19
- **Source:** `docs/BUILD_LIST.md` §4.1 (contested point 6), §20 (D10, D13, D26), §1.7

## Context

MongoDB Atlas already holds a working cluster with real users and examples, and the data is
document-shaped. Postgres would give a nicer window-function story for leaderboards and streaks, and the
credentials in the old repository were leaked and must be rotated. The question is whether the nicer
analytics story is worth a full data migration.

## Decision

**Keep MongoDB Atlas**, rotate the credentials in place rather than creating a new cluster (D13), and
express the one place Postgres would be nicer — leaderboards and streaks — as first-class Mongo
aggregation pipelines with `$setWindowFields` and compound indexes (§4.1 point 6, D10). Local development
uses Docker Compose with a seeded Mongo instance (D26).

## Consequences

- **Positive:** zero time cost (§4.1: "0"), no data migration, no model rewrite, and the existing users
  and examples are preserved — which is what makes the Phase 4 migration possible. The result is "a
  perfectly respectable interview answer".
- **Negative:** window functions must be written as aggregation pipelines instead of SQL, and the
  rotated Atlas credentials must be handled as a security incident (old tokens treated as compromised,
  history purged) rather than solved by discarding the cluster.

## Alternatives considered

- **Migrate to Postgres.** Gains `ROW_NUMBER`-style window functions for leaderboards but costs "a full
  data migration, a model rewrite, and losing the working Atlas setup" (D10) — no user-visible benefit
  (§1.7).
- **New Atlas cluster with clean data.** Would avoid migrating leaked credentials but discards real users
  and examples; D13 defaults to preserving them via in-place rotation.
- **Add a second analytics database.** Two stores for one small feature set is more operational surface
  than the feature justifies.
