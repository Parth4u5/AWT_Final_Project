# ADR-002: Use a pnpm-workspace monorepo with catalogs and Turborepo

- **Status:** Accepted
- **Date:** 2026-11-19
- **Source:** `docs/BUILD_LIST.md` §3, §4.1 (contested point 2), §20 (D23, D26)

## Context

A TypeScript migration of a two-app project has one dominant risk: type drift between client and server.
The legacy repository has two independent lockfiles and no shared contract, so a version bump in one app
can silently diverge from the other. The brief demands a "quality" answer even where it costs time:
"no speed development, no compromised optimisation or workflow".

## Decision

Adopt a pnpm workspace with **pnpm catalogs** and **Turborepo** as the task runner (§4.1 point 2, D23):

- One root `package.json` with `packageManager: pnpm@10.34.9`, a `pnpm-workspace.yaml`, a root
  `pnpm-lock.yaml`, and a `turbo.json` task graph.
- Catalogs declare every shared dependency version in one place, "so React/Zod/Vite can never drift
  between packages".
- Turborepo adds the task graph and a warm cache; its remote cache is ready for when the project goes
  public.
- Packages: `apps/web`, `apps/api`, `packages/shared`, `packages/engine`, plus shared `tooling/`
  presets. Local MongoDB via Docker Compose + a seed script is part of the same foundation (D26).

## Consequences

- **Positive:** dependency rot is structurally prevented; lint/typecheck/test/build run through one cached
  graph; `pnpm dev` needs no package build step (packages are consumed as raw TS source via aliases),
  while `pnpm build` still emits declarations.
- **Negative:** about half a day of setup (§4.1: "~0.5 day"), plus the discipline of adding every shared
  dependency to the catalog instead of pinning it locally. Two lockfiles from the old repo must be
  deleted in Phase 1 task 1.1.

## Alternatives considered

- **Plain `pnpm -r` without Turborepo.** Simpler, but no task graph and no warm cache; gives up the
  "quality" answer for a small saving.
- **Turborepo without catalogs.** Keeps the cache but leaves the actual prize — one declared version per
  shared dependency — on the table.
- **Keep two independent projects.** No shared contract, no way to make drift a compile error.
