# ADR-003: Use Fastify 5 instead of Express 5

- **Status:** Accepted
- **Date:** 2026-11-19
- **Source:** `docs/BUILD_LIST.md` §4.1 (contested point 3), §20 (D2, D28)

## Context

The legacy backend is Express with roughly eight endpoints and ad-hoc validation; the brief settles
every contested stack point "in favour of the quality option, including the ones that cost extra time".
The API needs to validate requests with the same Zod schemas the client already uses, present one uniform
error shape to a hand-written typed client, and cleanly host both the auth decorator and the AI tutor's
SSE route.

## Decision

Use **Fastify 5** for `apps/api`, with `fastify-type-provider-zod` and `setErrorHandler` (§4.1 point 3,
D2). The API remains a **separate service** rather than being merged into the SSR web app (D28).

## Consequences

- **Positive:** `fastify-type-provider-zod` "validates requests _and_ infers types from the same Zod
  schema the client uses" — one source of truth with no OpenAPI codegen. `setErrorHandler` gives "one
  uniform error shape for the typed client". Plugin encapsulation handles the auth decorator and the
  tutor's SSE route cleanly. Fastify has first-class TypeScript support.
- **Negative:** about two days of migration, partly offset by less glue code; the Express-era route and
  controller separation must be re-expressed as Fastify plugins. Keeping the API separate means two
  deployments, which is intentional: "sharing one process would couple the frontend's render lifecycle
  to the API's" (D28).

## Alternatives considered

- **Express 5 (legacy).** Familiar, but validation and inferred types come from separate layers, so the
  client and server can drift; error shapes are assembled per route.
- **NestJS.** "Far too heavy for ~20 endpoints, and a steep learning curve for the value it adds"
  (§1.7).
- **tRPC.** Would couple the client to the server and prevent a clean public API; REST plus shared Zod
  keeps the API portable (§1.7).
- **Merge the API into the web app.** Rejected because the web app is SSR and the API is a separate
  serverless service (D28).
